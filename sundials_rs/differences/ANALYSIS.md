# differences — analysis

Generated 2026-08-11T12:34:51Z from commit `bc4e2b3`.

## The short version

Over the 179 variants both sides run, the C built by Visual Studio 18
Professional and the pure-Rust port produce **identical output on
131** and **differ on 48**. On every one of those
48, "which side is right" was settled against the reference
outputs shipped with SUNDIALS 7.8.0:

| verdict | variants |
|---|---:|
| Rust matches the shipped reference, the C build does not | **41** |
| the C build matches the shipped reference, Rust does not | **0** |
| neither matches the shipped reference | **7** |

**There is no variant where the C build agrees with the upstream reference and
the Rust port does not.** Against the references overall:

| | byte-identical | whitespace-only | content |
|---|---:|---:|---:|
| **Rust port** | **153** | 15 | 11 |
| **C, built with MSVC** | 112 | 13 | 54 |

The Rust port reproduces the upstream references
**41 times more often** than the C does
when the C is compiled for this platform.


## Why — and it is not a defect in either implementation

The reference `.out` files shipped with SUNDIALS were generated on a **glibc**
host. A C program built here links the **Microsoft UCRT**, and the two C
libraries do not agree.
[`../evidence/windows-x86_64-ucrt/libm_fingerprint.txt`](../evidence/windows-x86_64-ucrt/libm_fingerprint.txt)
records the measurement: one Rust probe, built from the same source and run
natively on Windows and inside a glibc guest, hashing 1,000,000 results per
function. Only `sqrt` agrees. `sin`, `cos`, `tan`, `exp`, `ln`, `log10`,
`asin`, `acos`, `atan`, `sinh`, `cosh`, `acosh` and `pow` all differ.

The Rust port does not call the host libm at all. `sundials_libm` implements
those routines as translations of what glibc 2.39 runs on x86-64, each
measured bit-identical against a real glibc oracle over 8,000,000 inputs
(`../current_status.md` §2). So the **C** build follows the UCRT's rounding
and diverges from a glibc-generated reference, while the **Rust** build
follows glibc's rounding and reproduces it. That is the whole of the
48-variant gap: a statement about which C library each binary
links, not about the translation.

Inside an adaptive integrator the effect is amplified rather than averaged
away — a 1-ulp difference in one `exp` changes an error estimate, which
changes the next step size, which changes every step after it. Measured across
every numeric field that appears on a differing line:

| quantity | value |
|---|---|
| numeric fields on differing lines | 2115 |
| fields whose value differs at all | 1218 |
| fields differing in sign | 249 |
| largest absolute difference | 1e+19, in `cvsDiurnal_FSA_kry`, on values of order 1e23 |
| largest relative difference among fields of magnitude > 1e-6 | 1.92, in `cvKrylovDemo_ls`: `4.158e-06` vs `-4.510e-06` |

The large *relative* figures are all near-zero residuals — quantities like
`c1 (bot.left/middle/top rt.)` in the Diurnal family, printed at 1e-6 or
smaller while the solution itself is of order 1e11. Those are where chaotic
amplification shows first, and a sign flip there is not a magnitude error.


## The one hard failure, and it is on the C side

`cvsDiurnal_FSA_kry -sensi sim t` is the only variant on either side whose
output contains a solver error:

```
[ERROR][rank 0][.../cvodes.c:3504][CVode] At t = 56341.7023922865,
    mxstep steps taken before reaching tout.
SUNDIALS_ERROR: CVode() failed with retval = -1
```

That is the **MSVC C build**. It stops after 96 lines. The Rust port runs the
same problem to completion, prints 142 lines, and its output is
**byte-identical to the reference shipped with SUNDIALS 7.8.0**. The forward
sensitivity analysis in that example is stiff enough that the UCRT's `exp`
sends the step-size controller down a path that exhausts `mxstep`; reproducing
glibc's `exp` does not.

No Rust output on any variant contains an error marker, and neither does any
shipped reference. Note that this example still exits 0 — which is why the
harness scans output text rather than trusting exit codes.


## The 7 variants where neither side matches the reference

These are references the port's own verification already classifies as stale,
and the C build reproduces none of them either — independent corroboration
that the reference files, not the implementations, are the odd ones out.

| variant | what it is |
|---|---|
| `cvsKrylovDemo_ls` (4 argv variants) | shipped references have had trailing whitespace stripped, and were generated by a pre-2.27 glibc whose `sin` was correctly rounded |
| `ark_conserved_exp_entropy_ark 1 1` | the shipped reference is missing a final blank line the source prints unconditionally |
| `ark_harmonic_symplectic` | Rust vs reference is **whitespace-only**: every printed value matches, only column spacing differs (`SUN_TABLE_WIDTH` 28 → 29). The C differs in content. |
| `ark_kepler --stepper SPRK --step-mode fixed --count-orbits --use-compensated-sums` | same — Rust matches the reference on every value, the C does not |

So on two of these seven the Rust is right on the values as well, and only the
column width of a stale reference separates it from `same`.


## What was fixed as a result of this comparison

**Nothing in the Rust port**, because the comparison exposed no defect in it:
0 variants where the C is right and the Rust is wrong, 0 Rust
outputs with solver errors, and 153 of 179 reproducing the
upstream reference byte for byte. Changing the port to match the MSVC C build
would mean moving *away* from the reference outputs on 41
variants, which is the opposite of the acceptance criterion.

Two things *were* fixed in the measurement itself, both found while doing this
work:

1. **Exit codes were being trusted.** Several SUNDIALS examples print
   `SUNDIALS_ERROR` and still exit 0. The harness now scans every captured
   output for error markers and reports it as a column in
   [`../c-results/RESULTS.md`](../c-results/RESULTS.md) and
   [`../rust-results/RESULTS.md`](../rust-results/RESULTS.md). Without it the
   `cvsDiurnal_FSA_kry` failure above would have been recorded as a success.
2. **The four `*L` examples had no C counterpart.** They need LAPACK, which is
   not installed, so the main build skipped them and they would have been
   silently absent from the comparison. They are now built with exactly the
   substitution the Rust port makes — `SUNLinSol_LapackDense` →
   `SUNLinSol_Dense`, `SUNLinSol_LapackBand` → `SUNLinSol_Band` — so both
   sides run the same algorithm
   ([`../tools/build_c_lapack_substituted.cmd`](../tools/build_c_lapack_substituted.cmd)).
